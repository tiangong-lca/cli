# 文档撰写规范

本文件适用于 `docs/` 及其子目录。仓库根 [AGENTS](../AGENTS.md) 和 workspace 规则继续适用；本文件规定文档组织与维护方式，不重新定义 CLI 行为或交付授权。

## 文档职责

每份文档围绕一个明确主题，先确定读者、用途、适用范围及权威来源，再选择位置。优先更新已有的主题文档，避免另建一份重复说明。

| 文档类型 | 应承载的内容 |
| --- | --- |
| 接口设计与契约，如 `interfaces/` | 命令职责、输入输出、行为、边界与约束；按确定的设计规范撰写。 |
| 使用指南与参考 | 已实现能力的用法、可执行示例、版本要求及已知限制。 |
| 架构与开发约定 | 模块职责、依赖方向、稳定技术决策及开发验证方法。 |
| 实施计划与分析，如 `plans/`、`analysis/` | 阶段、依赖、验收条件、差距及待解决问题；明确其规划或分析性质。 |
| 运维与发布手册 | 部署、发布、恢复、排障、环境准备等操作程序及其前置条件。 |
| 历史记录与证据 | 指定时间、版本或事件的事实与结论；明确历史性质及当前替代入口。 |

目录名只是导航，文档的职责和实际内容必须一致。设计、实现、验证、部署和发布是不同状态：目标设计可以先于代码，指南中的可执行示例必须符合其声明的实现版本。

## 运维信息的边界

非运维文档不得嵌入部署与发布步骤、生产修复命令、主机地址和本机路径、账号清单、环境实例配置、运行编号、审批批次或现场排障记录。需要这些内容时，链接到对应所有者的运维手册或受控执行记录。

业务命令的权限要求、参数、错误语义、配置项名称，以及开发指南中的构建和测试方法，属于各自文档的必要内容。它们应使用通用示例；具体环境的取值和现场操作过程归运维文档。

运维文档也不承载密码、令牌、私钥或私人账号信息。受限的环境事实和执行证据保存在授权的记录中。其他仓库拥有的运维事实引用其权威入口，CLI 文档不维护副本。

## 长期规则与执行记录

长期文档规定稳定的行为和规则。具体工作分支、当次操作授权、临时文件位置、Issue 进度、某次测试计数、发布批次和交接命令，记录在对应 Issue/PR 或专门的执行记录中。

计划可以引用执行记录，但不把某次会话的选择升级为仓库通用约束。长期文档不追加逐次交付日志、评审留言或为了通过文档检查而添加的正文备注；完成文档评审后使用现有元数据记录评审事实。

## 过时信息的修正

- **现行文档原位更新。** 将失效规则、步骤、示例和限制改为当前适用的表述，删除被替代的内容，并同步检查相关表格、示例和链接。不能保留旧结论，再在末尾追加“现在改为……”来纠正它。
- **区分事实和目标。** 修改前确认文档描述的是现有实现还是确定的目标设计。实现尚未跟上设计时，在实现状态或计划中记录差距，不把目标契约退回为当前代码的能力清单，也不把目标示例当作已发布能力。
- **需要兼容时写清范围。** 仅在旧行为仍受支持或读者需要迁移时保留版本差异，明确适用版本、当前推荐方式和兼容边界，避免无日期的“以前”“现在”“最新”。
- **历史证据保持历史身份。** 不将原始执行记录改写成当前事实；被替代的文档注明历史范围和替代入口，从现行导航中移除或明确标识。可在历史记录旁补充有来源的更正，保留原始事实和更正来源的区别。
- **无法核实时明确缺口。** 标注待核实的具体事项和来源，不猜测、不宣称已验证。若影响现行操作，在执行前解决；一般的假设和讨论放入分析或计划。

Git 历史保留普通文档的修改过程。除专门的变更记录、迁移说明或历史材料外，正文以读者需要的当前结论为主，不复述修订经过。

## 权威来源与重复内容

产品规则以对应契约为准，实现能力以实际入口、代码及其验证为依据，依赖版本以 manifest 和锁文件为准，交付和发布状态以其权威记录为准。引用时保留必要的版本与适用范围，不仅凭聊天记录或过往计划确认事实。

同一规则由一个主要文档维护，其他文档提供必要摘要和链接。链接到具体主题或文件，不复制大段规则、命令清单和运维配置。产生冲突时先确认所有者和适用范围，再修正对应源文档及其引用。

## 表述与示例

- 先写文档解决的问题和适用范围，再说明行为、步骤或依据。使用明确的主语、动作和结果。
- 规范用语保持一致：必须、应当、可以分别表达约束、原则和可选能力；确定的接口设计直接规定行为，待定问题进入计划或分析。
- 命令示例使用真实支持的语法，注明占位符、必要前置条件和关键效果。涉及写入时说明写入对象与范围；不得让模拟结果看起来像真实服务验证。
- 标题、列表、表格和代码块服务于阅读，不堆砌同义结论、套话或无关实现细节。文件名和相对链接采用仓库现有约定。
- 新建或维护受治理文档时，使用现有 Docpact 元数据，准确填写用途、更新条件和已完成的评审事实。不得虚构评审、验证或发布状态。

## 完成前检查

1. 确认内容符合文档职责，运维细节、临时状态和历史过程已放在正确位置。
2. 检查旧结论是否已原位修正，相关示例和引用是否同步，适用版本与未验证事项是否清楚。
3. 按根 AGENTS 的 Docpact 入口完成路由、相关文档评审与 lint；治理配置有改动时运行严格配置检查。
4. 检查 Markdown 格式、链接和示例。仅文档变动不重复运行无关的业务测试；示例或操作行为需要验证时，按其风险执行对应检查。

维护既有文档时先整理与本次主题相关的过时内容；跨主题的大规模清理单独安排，并保留仍有价值的历史证据。
