# 数据审核

入口：`tiangong-lca review <action>`。Review 统一负责提交、重新提交、查询进度、读取材料和处理审核决定。Dataset 负责对象内容的创建、保存、查询与校验。

## 提交对象与审核包

Flow、Process、Model、Source、Contact 都可以独立作为提交对象，也可以共同组成一个审核包。提交者与审核者共享同一命令树，角色筛选不授予权限。

| 概念     | 含义                                                                     |
| -------- | ------------------------------------------------------------------------ |
| 提交对象 | 调用方明确选择的一个或多个数据对象，使用类型、标识、版本和内容修订定位。 |
| 关联范围 | 是否按业务依赖规则纳入关联数据，由 `includeRelated` 控制，默认 `true`。  |
| 审核包   | 本次审核固定的被审成员、参考材料、内容身份及关联关系。                   |
| 审核单   | 跟踪审核包的申请、轮次、意见、决定和进度，具有独立标识。                 |

单对象审核使用同一个提交接口：指定一个对象并设置 `includeRelated: false`，审核包中只有这个被审成员。审核包是本次业务审核的内容集合，不是导入导出的压缩文件，也不产生新的 Dataset 类型。

## 操作

| 操作 | 输入与前置条件 | 效果与结果 |
| --- | --- | --- |
| `submit` | `--input`：提交对象或审核包、关联范围、审核材料及请求身份。 | 解析并固定审核包，提交一次申请，返回审核单标识、包身份、成员清单及受理状态。 |
| `resubmit` | `--input`：原审核单及预期状态、新提交对象或审核包、关联范围、修改说明及请求身份。 | 关联原申请和新内容重新提交，返回实际审核单、轮次及前后包的关系。 |
| `get` | `--id`。 | 返回审核包身份、整体进度、成员状态、当前及历史决定、轮次和允许动作。 |
| `list` | `--role submitter` 或 `--role reviewer`、状态及分页条件。 | 返回有权查看的申请或待审项，携带范围与完整性信息。 |
| `materials` | `--id`、可选 `--round`、`--output`。 | 获取所选轮次的成员、参考材料、关联图、基线、差异、校验和证据清单。 |
| `comment` | `--input`：审核单、轮次、包或成员内容身份、意见、可选字段定位和请求身份。 | 追加针对明确内容的意见，返回意见标识，不形成决定。 |
| `decide` | `--input`：审核单、轮次、包身份、决定范围、预期状态、决定、依据和请求身份。 | 记录主体对整个包或明确成员的决定，返回成员及整体实际状态。 |
| `withdraw` | `--input`：审核单、预期状态、原因和请求身份。 | 在允许状态撤回申请，保留历史材料、意见和决定。 |

## 提交范围

`submit` 和 `resubmit` 接受两种互斥的选择方式：

- `targets`：给出起始对象清单，系统按关联范围解析最终审核包。
- `package`：给出明确审核包清单，包括 `members` 和所引用的材料。系统核验成员、关系及内容身份，不直接信任调用方声明。

两种方式都使用 `includeRelated`，省略时为 `true`。显式包清单中的被审成员同样作为展开起点；需要严格限定清单时设置为 `false`。关联范围关闭后，依赖检查仍会返回必要引用和阻断项，但不会把其他对象加入被审成员。

### 关联展开规则

1. 沿审核所需的出向业务依赖展开，不扩展到所有引用者或整库数据。例如 Process 可关联 Flow、Source 和 Contact；Model 可关联其精确 Process 及后续必要依赖。
2. 按领域规则区分被审成员与参考材料。起始对象保留明确的提交意图；关联数据中新增、修改或缺少适用通过结论的可审核对象纳入被审成员，已经通过且内容未变的对象保留为精确版本参考。决定可否复用仍由服务端规则验证。
3. Flow Property、Unit Group 等受治理的只读参考数据作为版本固定的参考材料，不因关联展开自动获得写入或独立审核能力。
4. 按精确对象及内容身份去重，保留多处引用关系；识别循环以终止重复遍历。同一数据版本出现冲突的内容身份时拒绝提交。
5. 每个成员返回起始或关联身份、纳入原因、内容版本及其与其他对象的关系。展开规则及其版本进入包的绑定信息。
6. 缺失引用、权限不足、前置状态不满足或展开达到限制时，明确返回阻断项与不完整范围，不静默跳过或将部分包报告为提交成功。

权限按每个被审成员和参考材料的实际角色检查。查看数据、将其作为参考材料及提交其审核是不同权限；不能通过父对象的权限代替所有关联对象的权限。

## 预览与内容固定

`submit --dry-run` 和 `resubmit --dry-run` 解析范围并返回最终成员、纳入原因、参考材料、阻断项和包摘要，不创建审核单或新轮次。预览可以写入 `--output`，不是提交的必经流程。

需要提交已预览的精确范围时，请求携带 `expectedPackageDigest`。实际提交重新验证对象、关系、规则和权限；包摘要不匹配时返回冲突，不提交另一组内容。预览摘要本身不授予权限。

实际受理绑定每个成员的类型、标识、版本及不可变修订或等价内容身份，并保证该内容可以再次获取。多次读取的临时集合不能自行宣称为一致的受理快照；无法固定完整内容时拒绝受理。后续数据保存不改变已经提交的审核包。

提交不隐式保存未声明修改。被审内容需要先通过 Dataset 创建或保存；本地校验报告不代替实际内容绑定、服务端校验或授权。整包提交是一个申请，不将失败的整包请求自动拆成多个单对象申请。

## 重新提交

`resubmit` 显式绑定原审核单、预期轮次和状态、新的 `targets` 或 `package`、修改说明及关联范围。默认同样包含关联数据。新包列明新增、修改、移除与不变成员，以及关联范围配置的变化。

未修改成员保留精确内容身份，不因重新提交而自动追新。修改后的对象必须提供新的内容绑定；新的依赖按本次范围和展开规则处理，不静默继承原包的范围或重新选择所有最新数据。

服务端决定沿用审核单新增轮次还是建立关联审核单；结果必须返回真实审核单、轮次和前后包关系。原始包、材料和决定保留。后续意见和决定必须指向实际轮次，不得将旧内容的通过结论直接复制给新内容。

## 进度、意见与决定

审核包整体进度、成员状态、主体决定及数据可见状态分别返回。`decide` 显式选择整个包或列出的被审成员，引用包身份和相关内容身份。针对某成员的决定不能扩展为对其他成员的决定；参考材料不能被隐式当作新的被审成员。

决定表达通过、驳回或要求修改。服务端根据成员完成情况、自审限制、多人审核和角色要求判定整体进度；一个成员或一个审核者的通过不代表整包完成。材料和成员权限不足时不得以包级操作绕过限制。

查询过滤的具体状态由领域契约提供并通过结构化帮助暴露。CLI 不用本地规则推断整体通过，也不把审核完成当作 Release 已发布。

`get`、`list`、`materials` 供具有相应权限的参与者使用。`comment` 允许授权的提交者答复或审核者记录意见；更正采用追加记录并关联原意见，不覆盖历史。分派审核者、撤销已生效决定和管理审核规则不属于本版操作集。

## 材料、失败与恢复

材料清单记录身份、摘要、来源和可读取状态。差异有明确比较基线，校验报告绑定内容与规则版本；缺失、未执行和无权读取分别标记。

专业判断由获授权的主体完成。AI 提交决定时保留真实执行主体与授权上下文，不冒充人工或独立审核。审核文件、校验结果和客户端角色声明不授予权限。

所有变更遵循[通用约定](conventions.md)，绑定环境、账号、请求身份、完整范围和内容。未知结果通过原请求查询或恢复，不重复创建申请、缩减成员或重新记录决定。撤回保留包历史；创建、保存和审核提交分别拥有成功条件。

## 与 Dataset 和 Release 的关系

Dataset 提供内容操作及 `validate`；Review 接收明确内容，负责申请与审核记录。五种可审核对象具有相同的 Review 提交入口，各类型的业务规则和实际权限分别验证。

Release 沿用现有接口，本轮不优化。审核决定与数据产品发布保持各自的业务结果和授权边界。

## 返回上下文与回复模板

审核操作遵循 [AI 上下文契约](ai-context.md)。`context.effectiveInput.includeRelated` 始终返回实际值；由默认规则选取时同时记录 `defaultedInputs`。

| 结果节点 | 关键事实 | 推荐后继与模板 |
| --- | --- | --- |
| 提交或重新提交预览完成 | 起始对象、被审成员和参考材料数量、规则版本、完整性、阻断项、包摘要及产物。 | `preview-result`；有现成且绑定精确范围的请求时可给出提交动作，否则说明缺少的输入。 |
| 提交或重新提交已受理 | 审核单、轮次、包身份、实际范围和成员数量。 | `operation-accepted`；首要推荐精确 `review get`，不默认作通过决定。 |
| 查询进度或读取材料 | 当前轮次、成员状态、整包状态、材料完整性和观察时间。 | `query-result`；按结果推荐材料读取、继续查询或所缺决定。 |
| 记录意见或决定完成 | 生效的意见或决定身份、作用成员或包、实际整包状态。 | `operation-completed`；不能把一个成员通过表述为整包通过。 |
| 内容、状态或预览包发生冲突 | 原包绑定、变化位置及可公开的当前状态。 | `conflict-result`；重新读取或预览，不自动调整审核范围。 |
| 提交结果未知 | 原请求、原始范围和恢复引用。 | `outcome-unknown`；核实原申请，不重新生成另一份申请。 |

大成员清单和完整差异写入产物，摘要保留数量、所有阻断类别和查看入口。审核包默认关联不自动变成需要用户再次确认的步骤；调用方有适用授权和明确范围时可直接执行。

## 示例

以下请求提交 Process，省略 `includeRelated` 即默认包含关联数据：

```json
{
  "requestId": "<request-id>",
  "targets": [
    { "type": "process", "id": "<process-id>", "version": "<version>", "revision": "<revision>" }
  ]
}
```

只审核一个 Source 时，显式关闭关联展开：

```json
{
  "requestId": "<request-id>",
  "targets": [
    { "type": "source", "id": "<source-id>", "version": "<version>", "revision": "<revision>" }
  ],
  "includeRelated": false
}
```

提交明确的多对象审核包时，使用 `package` 替代 `targets`：

```json
{
  "requestId": "<request-id>",
  "package": {
    "members": [
      { "type": "process", "id": "<process-id>", "version": "<version>", "revision": "<revision>" },
      { "type": "flow", "id": "<flow-id>", "version": "<version>", "revision": "<revision>" }
    ]
  },
  "includeRelated": false
}
```

```bash
# 可先预览；正式提交使用自己的请求身份及所需的预览摘要绑定。
tiangong-lca review submit --input process-review.json --dry-run --output review-preview.json --json
tiangong-lca review submit --input process-review.json --json
tiangong-lca review get --id <review-id> --json
tiangong-lca review materials --id <review-id> --output materials.json --json
tiangong-lca review decide --input review-decision.json --json

# 根据审核意见，通过 Dataset 保存修改后重新提交。
tiangong-lca review resubmit --input review-resubmission.json --json
```

重新提交请求包含 `reviewId`、预期轮次和状态、新内容选择、`changeSummary` 和请求身份；`includeRelated` 默认仍为 `true`。命令契约给出具体身份格式、所需材料及领域前置条件。
